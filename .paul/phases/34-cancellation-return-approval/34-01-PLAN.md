<objective>
## Goal
Enforce approval workflow di backend: PUT /requests/:id approval mengeksekusi perubahan order + ledger; PUT /orders/:id memblokir non-admin dari langsung set status cancelled/returned.

## Purpose
Tanpa perubahan backend ini, frontend bisa di-bypass — mitra tetap bisa langsung kirim `PUT /api/orders/:id { status: 'cancelled' }` meski UI sudah diganti. Backend harus jadi satu-satunya source of truth untuk status cancelled/returned.

## Output
- `requests.ts` — PUT approve handler dengan side effects: update order status + hapus ledger
- `orders.ts` — PUT handler memblokir non-admin dari set status cancelled/returned langsung
</objective>

<acceptance_criteria>

## AC-1: Approve request mengeksekusi perubahan order dan ledger
```gherkin
Given ActionRequest dengan status 'pending' dan type 'cancellation' atau 'return' ada di DB
When admin atau staff mengirim PUT /api/requests/:id dengan body { status: 'approved' }
Then response 200 dengan ActionRequest terupdate
  AND order terkait status berubah ke 'cancelled' atau 'returned'
  AND order.isBilled berubah ke false
  AND semua ledger entries dengan referenceId = orderId dihapus dari DB
```

## AC-2: Reject request tidak mengubah order
```gherkin
Given ActionRequest dengan status 'pending' ada di DB
When admin atau staff mengirim PUT /api/requests/:id dengan body { status: 'rejected' }
Then response 200 dengan ActionRequest status 'rejected'
  AND order terkait TIDAK berubah statusnya
  AND ledger terkait TIDAK dihapus
```

## AC-3: Non-admin tidak bisa langsung set order ke cancelled/returned
```gherkin
Given user dengan role mitra, staff, atau operational sudah login
When user mengirim PUT /api/orders/:id dengan body yang mengandung status: 'cancelled' atau status: 'returned'
Then response 403 dengan error message 'Pembatalan/retur harus melalui form pengajuan'
  AND order status TIDAK berubah di DB
```

## AC-4: Admin masih bisa langsung cancel/return order
```gherkin
Given user dengan role admin sudah login
When admin mengirim PUT /api/orders/:id dengan body { status: 'cancelled' }
Then response 200 dan order status berubah ke 'cancelled'
```

<task type="auto">
  <name>Task 1: Extend requests.ts PUT — approve side effects</name>
  <files>src/api/routes/requests.ts</files>
  <action>
    Tambah import `orders, ledgers` dari `../../db/schema.ts` (selain yang sudah ada: actionRequests, mitras).

    Di handler `router.put('/:id', ...)`, ganti logic yang hanya update actionRequests dengan:

    1. Fetch existing actionRequest dulu:
       ```ts
       const [existing] = await db.select().from(actionRequests).where(eq(actionRequests.id, req.params.id)).limit(1);
       if (!existing) return res.status(404).json({ error: 'Request not found' });
       ```

    2. Jika `req.body.status === 'approved'` DAN `existing.status === 'pending'`:
       - Update order:
         ```ts
         await db.update(orders)
           .set({ status: existing.type === 'cancellation' ? 'cancelled' : 'returned', isBilled: false, updatedAt: Date.now() })
           .where(eq(orders.id, existing.orderId));
         ```
       - Hapus ledger:
         ```ts
         await db.delete(ledgers).where(eq(ledgers.referenceId, existing.orderId));
         ```

    3. Update actionRequest dengan `{ ...req.body, updatedAt: Date.now() }`:
       ```ts
       const [updated] = await db.update(actionRequests)
         .set({ ...req.body, updatedAt: Date.now() })
         .where(eq(actionRequests.id, req.params.id))
         .returning();
       return res.json(updated);
       ```

    Tidak perlu transaksi — neon-http driver tidak support transactions (konsisten dengan keputusan existing: sequential inserts are safe for single-admin app).

    Jangan ubah role guard yang sudah ada (hanya admin/staff boleh PUT).
  </action>
  <verify>
    `npm run lint` — 0 TypeScript errors.
    Manual check: struktur handler — fetch existing → if approved: update order + delete ledger → update actionRequest.
  </verify>
  <done>AC-1 dan AC-2 satisfied: approve mengeksekusi side effects, reject tidak</done>
